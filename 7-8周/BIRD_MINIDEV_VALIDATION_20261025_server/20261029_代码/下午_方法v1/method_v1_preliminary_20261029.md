# 自校验 + 按需补 schema（method v1）Mini-Dev 500 初步结果

日期：2026-10-29

## 设计（预注册见 method_v1_PROTOCOL.md）

- C 组从普通 top-8 开始生成 SQL；sqlglot 解析 + SQLite authorizer 核验（越界读/执行报错）
- 缺失的表列名回检索器补入（含外键对端），最多 2 轮；近名列最多 2 组、各 5 个样例值
- A（普通 top-k）/ B（top-k+外键一跳）按每个模型 C 组实际平均 schema token 反选 k，只依据 token
- 严格 authorizer 评分：只允许读提示内 schema，越界判错；配对 bootstrap 1000 次
- 预注册判据：至少 2 个小模型 `strict_EX(C) − strict_EX(A) ≥ 3 pp` 且 95% CI 下限 > 0

## 观察

1. **外键一跳（B）在五个模型上都优于普通 top-k**（+0.4 / +1.4 / +4.9 / +2.8 / +6.6 pp），是这一轮最稳定的正向信号，API 上最明显（22.0% → 28.6%）。
2. **方法（C）没有跑赢普通 top-k**：两个模型 +1 pp 左右但区间跨 0，另两个略低。
3. 补 schema 触发了、越界也拦下了，但没有转化为执行准确率。可能原因（待验证）：
   - 样例值提示占掉 40–50 token，挤占了列覆盖；同 token 下 A 组的列更全；
   - 补 schema 只修“引用了不存在的对象”，修不了“列选错/连接写错”的语义错误；
   - 首轮只给 8 列，SQL 结构一旦写歪，二次生成很难救回。
4. 设计缺陷：提示里展示了近名列的样例值，但这些列不在最终可见 schema 里；模型若采用会被 authorizer 判越界（拦截量不大，但逻辑上应把这些列加入可见集，或只在模型已引用近名列时给值）。

## 局限

- 评分超时这次用 20 秒（此前实验 60/120 秒），少量重查询可能被判错；n=493/495。
- API 模型已补跑（deepseek-chat），五模型齐全；评分超时统一为 20 秒。

## 建议的 v2

1. 收紧样例值：只在生成的 SQL 已引用某近名列时提供该列的样例值，不预先展示；
2. 初始 k 提高到接近 A（如 12），让补 schema 做“增量修复”而不是“从 8 列重建”；
3. 补 schema 后只重写 SQL，不重新规划；对“列选错”类错误另设干预（如值匹配重排序）。
